# Регуляризованные бинарные классификаторы на признаках R3D-18

Этот эксперимент проверяет альтернативу неудачному дообучению backbone:
все блоки R3D и BatchNorm заморожены, изменяется только обычный `fc`.
Исходный checkpoint, разметка, ROI, 16 кадров, 4-секундные окна и split 30/10
сохраняются. Это классификация бинарных окон, не обучение типов нарушений.

Два кандидата фиксируются до новой оценки validation:

- `l2_logistic`: полнобатчевая взвешенная cross-entropy с L2=1.0 на весах;
  LBFGS ограничен 250 итерациями и критерием сходимости только по train.
- `shrinkage_lda`: взвешенный линейный дискриминант с 90% усадкой pooled
  covariance к диагонали и фиксированной добавкой 0.001 для устойчивости.

Среднее и масштаб признаков вычисляются только по train с теми же вероятностями,
что задают баланс классов/канонических видео и смесь 80% оригиналов / 20%
аугментаций. Матрица вероятностей не делает копии независимыми примерами.
Нормализация алгебраически сворачивается в `nn.Linear(512, 2)`: существующие
`load_checkpoint`, сканер и API не требуют новой реализации модели.

Сохранённые checkpoint предназначены для инференса; старое состояние optimizer
не выдаётся за пригодное для возобновления после преобразования координат.
Для воспроизведения сохраняются параметры solver, нормализация, train-bank,
конфигурация, хеши и исходный checkpoint. Новый solver не читает validation.

Запуск из корня с `PYTHONPATH=src`:

```bash
python -m overfitted_underqualified.ml.regularized_heads --config configs/r3d18_regularized.yaml
```

Каждый запуск создаёт новый `runs/r3d18_regularized_<UTC>/`:
`l2_logistic/last.pt`, `shrinkage_lda/last.pt` и приватный `train_features.pt`.
Никакие прежние runs не перезаписываются. Извлечение train-признаков идёт
на CUDA, небольшие регуляризованные задачи решаются на CPU с двумя потоками.

Перед validation сохраняются обе модели. Затем прежний checkpoint и оба
кандидата оцениваются одинаково: все известные положительные отметки,
одно центральное отрицательное окно, максимум scores внутри канонического видео,
порог 0.5. Отдельно оцениваются 40 аугментированных validation-потомков.
Веса не подбираются по validation; итоговое сравнение кандидатов относится
к development-выборке, а не независимому test.

Отчёты находятся в `reports/regularized_study_<UTC>.json/.md` и
`reports/evaluation_regularized_<UTC>/`. Они содержат метрики train/validation,
ошибки, scores и численную provenance. Банковских кадров и весов в отчётных
архивах нет. `.env`, backend и выбор активной модели не меняются автоматически.

Ограничения прежние: 30/10 видео одного кабинета, неизвестные связи сеансов,
многократный просмотр validation и отсутствие нового реального test. Увеличение
метрики на десяти известных видео не доказывает перенос на новые операции.
