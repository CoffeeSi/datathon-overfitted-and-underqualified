# Детектор банкнот и последовательность обслуживания

Итоговый [отчёт 18.10.2026](../reports/banknote_study_20261018.md): купюры F1=0.80
на отдельных validation-точках; сопровождение позволяет найти X-38 @ 29 s,
ошибка 4 s относительно action-отметки 33 s. На четырёх просмотренных сетках
TP=1/TN=3/FP=0/FN=0. Это минимальная исследовательская приёмка одного сценария,
не независимая оценка юридических нарушений. Полная история попыток сохранена.

Исследование дополняет существующий R3D-18 отдельным пространственным детектором
`ml/banknote_model.py`. Вход детектора — конечный RGB-кадр; он ищет **лежащие на
столе банкноты**, возвращает их рамки и score. Документы, банкноты в руках и в
машинке не являются положительной целью. Это объектный признак, а не нарушение.

Tiny U-Net обрабатывает crop при ширине 512 px. Рамки дают приближённые маски,
поэтому результат нельзя считать оценённой точной сегментацией. R3D продолжает
определять клиента и передачу наличных по 16 кадрам предыдущих двух секунд.
`PrimitiveScanner` заменяет только cash-score и применяет прежнюю цепочку
`CashSequence`: приём → уход клиента → деньги сохраняются на столе.
В инференс передаётся только видео; CSV и известные отметки не используются.

## Источники и split

`events.csv` остаётся единственным редактируемым источником разметки. В существующих
`primitive_review.points` добавлены `banknote_boxes` (нормированные xyxy),
`banknote_boxes_complete` и метод просмотра. В train размечены 52 кадра: 12 с
банкнотами и 40 без этого признака, восемь канонических видео. Неуверенные и
перекрытые положительные кадры без рамок исключены. Все прежние поля, action-метки,
исходные таймстампы и байты split сохранены.

Предоставлены 168 аугментаций 42 источников. Аудитор `ml/supplemental_data.py`
сопоставляет родительские ID, включая X-47→X-4 и X-48→X-5, проверяет SHA,
тайминг, размеры и соответствие CSV текущим events. Из них 128 строк относятся к
train (120 вариантов после объединения точных канонических копий), 40 потомков
validation запрещены для обучения. Исходный split остаётся 30/10.

Для каждого размеченного train-кадра выбирается оригинал либо проверенный
warm_sepia/cool_camera/cctv_low_quality вариант. Число примеров и вес исходного
кадра не умножаются на число вариантов. Внешние бинарные метки не становятся
объектными метками; рамки наследуются из просмотренного родителя. Зеркальные
варианты поддержаны с обратным преобразованием до crop, но текущий запуск их
не использует.

`annotations.xlsx` описывает четыре сгенерированных сценария S01–S04 и их
зеркальные копии. Это четыре синтетических источника, не восемь независимых
реальных сцен. Описания сохраняются как предоставленные утверждения, SHA сверены
с файлами;
для данного детектора они не использованы: рамок для его точной цели нет.
`scenario_01_clean.mov` без соответствующей разметки остаётся исключённым.

## Воспроизводимый запуск

Из корня установите `PYTHONPATH=src`; PowerShell: `$env:PYTHONPATH='src'`.
Пути внешних данных задаются аргументами, поэтому аудит можно повторить на Brev.
Аудит и кадры остаются в игнорируемом `data/local_artifacts/`; внешние файлы не изменяются.

```sh
python -m overfitted_underqualified.ml.supplemental_data --augmented-dir PATH/videos_augmented --labels PATH/labels_augmented.csv --synthetic-dir PATH/videos --workbook PATH/annotations.xlsx --output data/local_artifacts/supplemental_audit_NEW.json
python -m overfitted_underqualified.ml.banknote_model --config configs/banknotes.yaml
python -m overfitted_underqualified.ml.banknote_model --config configs/banknotes.yaml --train
python -m overfitted_underqualified.ml.banknote_evaluation --primitive-checkpoint runs/PRIMITIVES/last.pt --banknote-checkpoint runs/BANKNOTES/last.pt --output-dir reports/evaluation_banknotes_NEW --device cuda
python -m overfitted_underqualified.ml.primitive_inference --checkpoint runs/PRIMITIVES/last.pt --banknote-checkpoint runs/BANKNOTES/last.pt --video PATH/video.mp4 --output data/local_artifacts/scan_NEW.json --device cuda
```

После нового аудита внесите путь и SHA manifest в новую конфигурацию. Для нового
обучения требуется новый `output_dir`. Предыдущие веса, метрики и источники не
перезаписываются. Checkpoint содержит архитектуру, параметры, exact source
manifest и provenance использованных вариантов. При загрузке веса не скачиваются.
Для инференса Desktop-данные не требуются.

Текущий `configs/banknotes.yaml` запускает **30 дополнительных эпох v3 из весов
v2**, а не обучение с нуля. Он ссылается на
`runs/banknotes_balanced_20261018T021500Z/last.pt` и его точный SHA-256 через
`initialize_checkpoint` и `initialize_checkpoint_sha256`. Полученный checkpoint:
`runs/banknotes_finetune_20261018T021538_229103Z/last.pt`.
Начальные веса нужны для повторного обучения; готовый итоговый checkpoint
восстанавливается самостоятельно.

Полное повторение двух этапов начинается с копии `configs/banknotes_balanced.yaml`:
задайте новый output и выполните 60 эпох v2. Затем в копии `configs/banknotes.yaml`
укажите полученный checkpoint, его SHA и новый output для 30 эпох v3. Если пути
внешнего аудита меняются при переносе на Brev, сначала создайте там аудит и
проведите оба этапа с одним и тем же manifest. Инициализация проверяет полное
совпадение manifest, включая provenance вариантов; смешивать родительские веса
с заново составленным несовпадающим manifest нельзя.

В 01 показаны покрытие и аудит. В 02 — конфигурация, просмотр рамок, явный запуск
и loss. В 03 — `EVAL_PROTOCOL=banknotes`, метрики, confusion matrices, ошибки,
полная траектория и ZIP. По умолчанию `RUN_BANKNOTE_TRAINING=false` и
`RUN_BANKNOTE_EVAL=false`; просмотр кадров также включается отдельно.

## Необязательное сопоставление изображений между детекциями

Флаг `--track-banknotes` включает `ml/banknote_tracking.py` при полном проходе.
Он использует те же веса детектора и добавляет проверку изображения, когда
покадровая детекция пропадает. Без флага сохраняется прежний проход только с
детектором. Для двух вариантов создавайте разные отчёты:

```sh
python -m overfitted_underqualified.ml.banknote_evaluation --primitive-checkpoint runs/PRIMITIVES/last.pt --banknote-checkpoint runs/BANKNOTES/last.pt --track-banknotes --output-dir reports/evaluation_banknotes_tracked_NEW --device cuda
python -m overfitted_underqualified.ml.primitive_inference --checkpoint runs/PRIMITIVES/last.pt --banknote-checkpoint runs/BANKNOTES/last.pt --track-banknotes --video PATH/video.mp4 --output data/local_artifacts/scan_tracked_NEW.json --device cuda
```

Начальная рамка должна прийти от детектора с score не ниже 0.7. Для её продолжения
на каждом следующем **переданном кадре** требуется новое совпадение текстурного
фрагмента: нормированная корреляция OpenCV не ниже 0.9 и средняя абсолютная разница
RGB не выше 12 на шкале 0–255. Одного прошлого score или сохранённого времени
недостаточно. Поиск ограничен небольшим смещением: 1.5% размеров кадра за шаг,
3% относительно последней рамки, полученной от модели. Шаблон между модельными
детекциями не обновляется, чтобы постепенно не сместиться на фактуру стола.

При несовпадении, недостаточной текстуре, изменении геометрии, слишком большом
смещении или разрыве наблюдений больше двух секунд трек удаляется. Также действует
эвристическая проверка резкого изменения общего изображения. Продолжение по
совпадению не продлевает срок: после десяти секунд без новой модельной детекции
трек истекает. Новая детекция может обновить шаблон и время последней детекции.
Каждое видео получает отдельный трекер; между роликами память не переносится.
При проходе с шагом 1 s это проверка последовательности выбранных кадров,
а не непрерывное наблюдение каждого кадра видео.

В результатах различаются `evidence_type=model_detection` и `tracked`. Для
продолженного объекта сохраняются исходный `model_score`, корреляция
`tracking_score`, RGB-разница, времена первой и последней модельной детекции,
время текущего совпадения и `track_id`; причины удаления записаны в
`tracking_evidence`.
`banknote_tracking_config` со схемой `banknote_image_tracker_v1` сохраняется
в полном scan и отчёте вместе с SHA обоих checkpoint и источников данных.
Включение этого режима не меняет веса, разметку, split или пороги временной цепочки.

**Tracked score не является калиброванной вероятностью.** Код вычисляет
`min(model_score, tracking_score)`: первый член — средний sigmoid-score пикселей
компоненты, второй — нормированная корреляция изображений. Эта операция не
оценивает вероятность наличия банкноты и не проходит вероятностную калибровку.
Значение используется как эвристическая оценка свидетельств для прежних порогов
цепочки; название совместимого поля `probabilities` этого не меняет. Исходные
детекции отдельно доступны в `detector_objects` и `raw_detection_score`.
Итоговый `confidence` кандидата, объединяющий эти оценки, также не является
вероятностью юридического нарушения.

Совпадение изображения поддерживает только исходную объектную гипотезу. Ошибочно
распознанный документ также может совпасть с шаблоном; трекер не доказывает
семантический тип, тождество купюр или принадлежность денег. Для всех результатов
сохраняется `absence_certified=false`. Отсутствие трека не подтверждает пустой стол.

Метрики 39 отдельных validation-точек по-прежнему считаются без трекера: у таких
точек нет последовательного контекста его состояния. Влияние флага измеряется
отдельно на полных траекториях и ограниченной выборке просмотренных сеток кадров.
Эти результаты нельзя подменять метриками отдельных кадров или считать
независимой оценкой: решение проверить трекер принято после диагностики пропусков
в предыдущем validation-проходе.

## Протокол и ограничения

До первого validation-прогона этого детектора сравнивались только диагностические
результаты на размеченных train-кадрах. История попыток сохранена:

- V1, 60 эпох: 0 из 12 положительных train-кадров обнаружены. Исходные конфигурация
  `configs/banknotes_initial.yaml` и run `banknotes_augmented_20261018T020455Z`
  сохранены; старый checkpoint восстанавливается с прежней ReLU.
- `balanced_bce_dice_v2`, 60 эпох, learning rate 0.001: обнаружены 12 из 12
  положительных train-кадров, но 25 из 40 отрицательных дали ложные детекции.
  BCE раздельно усредняет положительные и отрицательные пиксели, Dice применяется
  к положительным кадрам, используется LeakyReLU. Конфигурация
  `configs/banknotes_balanced.yaml` и run `banknotes_balanced_20261018T021500Z`
  сохранены.
- `hard_negative_bce_dice_v3` с нуля, 60 эпох, learning rate 0.001: снова 0 из 12
  положительных train-кадров. Конфигурация `configs/banknotes_hard_negative.yaml`
  и run `banknotes_hard_negatives_20261018T022500Z` сохраняют эту неудачную попытку.
- Итоговый запуск: веса последней, 60-й эпохи v2 → **30 эпох v3 при learning rate
  0.0001**. Новый AdamW не восстанавливает состояние старого оптимизатора. V3
  уделяет градиент отрицательной части loss наиболее ошибочным фоновым пикселям:
  top-k ограничен числом доступных отрицательных пикселей, с целевым отношением
  3 к положительным и минимумом 1% фона. Параметры закреплены в
  `reports/banknote_finetune_plan_20261018.json` до оценки validation.

У всех попыток сохранены seed 42, порог 0.7, минимальная компонента 6 px,
геометрия и прежние параметры временной цепочки. Выбирается последняя эпоха;
validation не обновляет веса и не используется для подбора эпохи или порога.
Полный итоговый путь включает 60 + 30 обучающих эпох, хотя в финальном checkpoint
`epoch=30`: родительские 60 эпох отражены в `initialization`. Train-диагностика
не является оценкой обобщения; итоговые validation-метрики берутся из отдельного
отчёта полного прохода, а не из этих чисел.

Оценка имеет три разных основания:

- 39 ранее размеченных validation-точек для видимых примитивов;
- все 10 validation-видео для поиска кандидатов и сопоставления с известной
  положительной action-отметкой; полнота юридической разметки не подтверждена,
  поэтому legal Precision/F1 не вычисляются;
- отдельный визуальный сценарий на полностью просмотренной сетке с шагом 1 s
  в X-2/X-31/X-38/X-39. Его video-level и temporal-метрики относятся только к
  этим четырём видео. Проверка хранится в `primitive_review.sequence_grid_review`;
  это не непрерывная юридическая экспертиза и не человеческая аттестация.

Ссылки на правила берутся из существующего каталога по единственному типу
кандидата `unsecured_accepted_cash`. Принадлежность денег, завершение операции
и проводка по видео не устанавливаются. Отсутствие сегмента означает отрицательный
прогноз детектора, а не подтверждённое отсутствие банкнот: оно может сбросить
память цепочки и привести к пропуску. Возвращается `research_candidate` либо
`insufficient_data`, а не автоматическое юридическое решение.

Кабинет и участники общие, сеансы неизвестны, validation многократно использовалась
для диагностики. Прежний FastAPI-контракт сохранён; эксперимент не включается
автоматически в сервис. Кадры не сохраняются в notebook outputs или отчётные ZIP.
