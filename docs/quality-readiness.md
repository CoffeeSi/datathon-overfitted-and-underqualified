# Проверка качества и доказательств перед расширением типов

Текущий результат: [аудит покрытия](../reports/quality_coverage_20261018_current/report.md)
и [очередь сбора/проверки](../reports/quality_coverage_20261018_current/collection_queue.json).
Это воспроизводимая проверка данных, а не новый эксперимент с качеством модели.
Бинарные веса с accuracy 60%, `events.csv`, каталог и split не изменены.

## Что показал аудит

Из десяти каталожных типов только `unsecured_accepted_cash` и
`client_identity_check_not_visible` имеют положительные метки и в train, и в
validation. У обоих лишь один положительный канонический источник в каждой
выборке. X-4/X-47 — одно видео с двумя отметками, а не два независимых примера.
Для `safe_key_left_in_lock` есть два train-видео, но нет положительного validation.
`cash_counted_without_client_present` представлен положительным X-34 только в
validation. Для ухода кассира во время обслуживания нет подтверждённых
положительных action-меток ни в одной выборке.

Остальные типы также не имеют достаточного покрытия обеих выборок. Часть меток
доступна как пакетное утверждение, а не просмотр кадров: аудит показывает это
отдельно и не меняет существующие метки задним числом. Отрицательное окно
не считается отрицательным видео целиком. Полной временной разметки всех
положительных видео нет, поэтому полноценный event-level test не объявляется готовым.

Приоритет: новые реальные положительные примеры типов, отсутствующих в train;
затем разнообразные положительные случаи и похожие нормальные операции для двух
типов, представленных в обеих выборках. Цели 5 train-положительных и 2
validation-положительных на тип в очереди — ориентиры для сбора, не статистическая
гарантия. Группировать нужно по реальному источнику/сеансу, не по имени файла.

## Как повторить

Из корня с установленными зависимостями и `PYTHONPATH=src`:

```bash
python -m overfitted_underqualified.ml.quality_audit
```

Будет создан новый `reports/quality_coverage_<UTC>/`: `audit.json`, `report.md`
и `collection_queue.json`. Опциональный `--synthetic-dir PATH` разрешает проверить
перемещённые синтетические исходники по SHA-256; он не импортирует их разметку.
Файлы и хеши исходных видео проверяются, labels/split не записываются.
В конце `01_eda.ipynb` есть интерактивное представление покрытия и пробелов.

## Строгое сопоставление для ML/Backend

Новый интерфейс — `overfitted_underqualified.rules.evidence.grounded_rule_match`.
Его входы: предполагаемый `event_type`, словарь конкретных визуальных фактов
`True/False/None` и происхождение доказательства `evidence`.

- Обязательные факты заданы в `VISUAL_REQUIREMENTS` для каждого типа.
- Нужны SHA-256 видео, идентификатор основания, минимум два возрастающих времени.
- Допустимы просмотр последовательности кадров или отдельно оценённый action/
  object-sequence компонент. Для модели требуются SHA-256 checkpoint и отдельное
  `quality_approved=True`. Ни одной новой модели этот статус здесь не присвоен.
- `binary_r3d18` и один score не являются доказательством типа.
- Если обязательного факта нет, он неизвестен/опровергнут либо provenance
  недостаточен: `event_type=None`, `source_links=[]`, `rule_status=unresolved`.
- Если визуальное основание достаточно: ссылка остаётся
  `conditional_reference`, `requires_review=True`, `legal_conclusion=None`.
  Условия применимости и то, что видео не устанавливает, возвращаются отдельно.

Вызывающий код отвечает за правдивость фактов и приёмку качества компонента:
проверка структуры не заменяет просмотр или распознавание. При инференсе факты
получают из текущего видео, а не из `events.csv` или имени файла.

`source_links_for` остаётся справочным lookup каталога; наличие ссылки не
разрешает публиковать тип. `event_type_for_observed` возвращает только предложение,
и теперь использует те же ограничения неоднозначных тегов, что action-обучение.
Неизвестное содержимое сумки, предполагаемые наличные и сам уход от стола
не подтверждают определяющие условия. Явные существующие action-review
сохранены отдельно от этих предложений; X-38 не теряет свою проверенную метку.

Backend/frontend, wire schema, настройки провайдера и legacy `link_action`
не изменялись: тиммейт подключает сервис параллельно. Для нового строгого пути
ему нужно вызывать `grounded_rule_match` перед созданием typed finding и
оставлять unresolved при `event_type=None`. Legacy lookup/обогащение сами
этого шлюза не вызывают; их нельзя выдавать за проверку визуальных условий.

## Независимый test и дополнительные материалы

Владелец подтвердил, что новых реальных сеансов нет. Из прежних validation-видео
нельзя сделать невиданный test переименованием. 168 аугментаций сохраняют связи
с X-*, а 9 синтетических файлов — это четыре сценария с зеркальными версиями
и один неразмеченный файл. Они не доказывают перенос на реальные новые сеансы.

`assess_holdout_candidate` проверяет будущие intake-метаданные: реальное
происхождение, проверенную новую группу источника, отсутствие предыдущего
использования и производности, новый SHA-256 и проверенные метки. Функция
не назначает split и не создаёт второй источник разметки: метки остаются в events.csv.
Без этих данных итоговый test и подтверждение независимого качества остаются открыты.
