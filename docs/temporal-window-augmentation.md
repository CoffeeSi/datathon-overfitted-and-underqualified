# Окна с временным сдвигом вокруг положительной отметки

Эксперимент меняет только представление train-примеров во времени. Он следует
за двумя неудачными регуляризованными классификаторами; их результаты сохранены
в `reports/regularized_study_20261018T035417_731553Z.json/.md`.

Для каждой положительной отметки из `events.csv` добавляются центры окна
на -1 и +1 секунду. Окно остаётся четырёхсекундным и содержит исходную отметку.
Обрезка у границы проверяется явно; дубликаты центров не добавляются.
Отрицательные окна не сдвигаются, неразмеченные участки положительных видео
не объявляются фоном. X-4/X-47 сохраняют две разные опорные отметки одного видео.

Новые окна и четыре проверенные визуальные версии дают 170 дополнительных
представлений, всего 605 train-окон. Это по-прежнему 30 канонических train-видео,
а не 605 независимых случаев. Взвешивание сохраняет одинаковую массу классов и
канонических видео внутри класса, смесь — 80% оригиналов / 20% преобразований.

Backbone/BatchNorm заморожены. Используется прежний `fit_head`: seed 42,
120 обновлений, batch 16, lr 0.0003, weight decay 0.0001. Порог — 0.5;
checkpoint фиксирован по последнему шагу. Эти параметры не подбираются по
validation. Контроль на первоначальном feature bank воспроизвёл прежнюю голову
побитно до обучения нового варианта.

```bash
python -m overfitted_underqualified.ml.temporal_jitter --config configs/r3d18_temporal_jitter.yaml
```

Запуск из корня с `PYTHONPATH=src`. Конфиг содержит точные пути к исходному
checkpoint и train-bank предыдущей фазы. Для другого checkout сначала нужно
перенести эти приватные артефакты либо выполнить фазу регуляризованных голов и
указать её новые пути. SHA-256 и соответствие исходников проверяются до reuse;
признаки другого backbone, разметки или split не принимаются.

Дополнительные train-признаки извлекаются из видео; исходные 435 переиспользуются
только после проверки provenance. Отчёт сохраняет `event_anchor_sec`, новый
центр, границы окна, связи исходных ID и хеши. `events.csv` остаётся единственным
редактируемым источником меток и времени. Изменений backend, `.env` и назначения
видео в split нет; новые веса записываются в отдельный `runs/`.

Основная оценка — те же окна вокруг известных положительных отметок и одна
середина отрицательного видео, с агрегацией максимумом по каноническому видео.
Отдельно оцениваются 40 связанных validation-потомков. Это development-оценка:
многократно просмотренная validation одного кабинета не заменяет новый test.
